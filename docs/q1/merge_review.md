单目标兼容入口 `solve_file(..., cores=5, seconds=600)` 仍可用。它只请求一种核数；循环四次会建立四份独立预算，不是整case验收方式。正式四核数运行必须一次调用 `solve_case(..., cores=[2,3,4,5], seconds=600)`，当前100case脚本已这样调用。

## 复核中修正的问题

1. **近似新增搬运量基数错误。** 原估计器将原图搬运量初始化为0，校准时读取 `original_copy_bytes`，而官方输出字段是 `original_graph_copy_bytes`，导致原图必要搬运被算成新增搬运。对同一份case001/5核方案，修复前复现值为1,644,160 byte，官方值为4,608 byte；修复后无需任何官方校准，近似新增搬运量即为4,608 byte。
2. **图特征与搬运统计共用正确的COPY方向。** 原始图搬运量直接按官方定义统计COPY_IN的输出和COPY_OUT的输入，而不是相反一侧或简单累加所有张量。特征与近似评估共用该函数。原始字节数是静态图信息，不是单核运行成绩；官方校准会拒绝与当前图基数不一致的样本。
3. **旧报告的计时说明及汇总。** `report_unified.py` 改为读取case根摘要的时钟与超时标记，不用四个核数的用时和替代整case总时间；拒绝旧逐核预算输入。缺少单核分母会明确标记，不补计历史秒数。报告按实际请求集合说明覆盖，不把16项写成400项。
4. **过时说明。** 配置中的“官方裁决”改为近似和官方均可接纳、官方按预算校准。历史近似审计、分批复测、暂停记录加版本声明；旧分批报告工具拒绝当前整case数据，避免重新生成旧口径。公共CLI补充总预算帮助，单目标接口和文档补充误用提醒。

第1、2项是正确性修复，会影响搬运特征及周期相同或接近时的候选比较。不能再把最终版本的全部自适应轨迹称为与旧快照完全相同。比较键仍是原来的 `(makespan, added_copy_bytes)`，改变的是此前错误的估计字段；没有改官方目标或引入历史答案。

## 复现与剩余边界

```powershell
$env:PYTHONPATH='src;tests'
$env:PYTHONUTF8='1'
$env:PYTHONIOENCODING='utf-8'
python -B -X utf8 -m unittest discover -s tests -v

python -B -X utf8 tools/benchmark_unified.py --data official/data `
  --config official/data/config.txt --cases 1 6 14 56 --cores 2 3 4 5 `
  --seconds 30 --local-test-workers 4 --output outputs/merge_review_reproduce
python -B -X utf8 tools/audit_unified.py --run outputs/merge_review_reproduce `
  --replay --require-current-source --local-test-workers 4
python -B -X utf8 tools/report_unified.py --run outputs/merge_review_reproduce `
  --report outputs/merge_review_reproduce/REPORT.md
```

原始case文件与冻结快照不随代码上传；缺少快照时对应差分测试会额外跳过。限时复跑可能因机器负载改变搜索轨迹；JSON提供本次源码、计划和官方结果哈希以区分运行。

近似仍未完整模拟Spill与内存复用依赖，`spill_added_copy_bytes=None`不表示0；内存可行性仍以官方评估为准。成本估计不是每次调用的硬上界，监督进程负责整case保护。局部近似微小收益可能误排，尚无全图最优或所有输入性能保证。上述边界已明确写入现行说明，不能用“通过接口测试”替代后续Q3或全量性能实验。
